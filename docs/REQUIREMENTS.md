# QLStats — технические требования

QLStats собирает статистику игроков с одного сервера Quake Live через ZMQ и показывает её участникам на веб-странице. Формат событий разобран в [research/ql-zmq-events.md](research/ql-zmq-events.md). Архитектура описана в [ARCHITECTURE.md](ARCHITECTURE.md).

Пометка **[решение]** стоит там, где вариант выбран при проектировании, а не задан заказчиком.

## 1. Источник данных

- Подключение — ZMQ SUB к PUB-сокету QL-сервера с пустой подпиской. Сообщение состоит из одного фрейма: UTF-8 JSON вида `{"TYPE": ..., "DATA": {...}}`.
- Аутентификация — ZMQ PLAIN, логин `stats`, `ZAP_DOMAIN = "stats"`.
- Параметры задаются переменными окружения `QL_ZMQ_HOST`, `QL_ZMQ_PORT`, `QL_ZMQ_USER`, `QL_ZMQ_PASSWORD`. Шаблон лежит в `.env.example` в корне репозитория. Остальные параметры: `QLSTATS_DB_PATH`, `QLSTATS_HTTP_ADDR`, `QLSTATS_TZ` (по умолчанию `Europe/Moscow`), `QLSTATS_LIVE_OFFLINE_SECS` (по умолчанию 15).
- Приложение работает на отдельной машине, а не на игровом сервере. Связь с сервером идёт по сети.
- Секреты в git не попадают: `.env` есть в `.gitignore`, в репозитории хранится только `.env.example` без настоящего пароля. Пароль не пишется в логи.

## 2. Хранилище

- Используется SQLite, один файл.
- Каждое полученное сообщение сохраняется как есть: тип, время получения (UTC, мс), `MATCH_GUID` (если удалось извлечь) и исходный JSON. Сырой текст сохраняется и тогда, когда JSON не разобрался; тип в этом случае пишется как `_INVALID`.
- `MATCH_GUID` есть во всех событиях, которые связаны с матчем. Живая запись подтвердила его и в `PLAYER_MEDAL`, так что медали тоже привязываются к матчу.
- Из сырых событий строятся нормализованные таблицы (матчи, участники матча, смерти, игроки) и агрегаты. Все производные данные можно в любой момент полностью пересчитать из сырых событий.

## 3. Правила учёта

### 3.1 Какой матч засчитывается

Матч засчитывается (`counted`), только если выполнены все условия:

1. Получен `MATCH_REPORT` с `ABORTED = false`. Матч с `ABORTED = true` не засчитывается.
2. Перед этим `MATCH_REPORT` получен `MATCH_STARTED` с тем же `MATCH_GUID`. Если `MATCH_STARTED` нет (например, потерян из-за обрыва), матч не засчитывается.
3. `GAME_TYPE` — `FFA` или `DUEL`. Командные режимы (`CA`, `TDM`, `CTF`, `ONEFLAG`, `FT`, `AD`, `DOM`, `RR`, `HAR`) исключаются из всей статистики: они не попадают ни в таблицу, ни в счётчики матчей. `RACE` — открытый вопрос (раздел 6). До его решения `RACE` не засчитывается **[решение]**.
4. В матче участвовали минимум 2 человека. Если за весь матч был только один живой игрок, матч исключается целиком.
5. Матч с этим `MATCH_GUID` ещё не учтён. Повторный `MATCH_REPORT` с тем же GUID игнорируется.

Если матч не засчитан, его запись остаётся в таблице `matches` с `counted = 0` и указанием причины. Его данные не входят ни в какие показатели.

### 3.2 Warmup

События с `WARMUP = true` игнорируются везде, в том числе `PLAYER_STATS` и `PLAYER_DEATH`.

### 3.3 Боты и люди

- В блоках `KILLER`/`VICTIM` игрок считается ботом, если `BOT = true`. В остальных событиях ботом считается игрок с `STEAM_ID == 0` (строка `"0"` или число `0`).
- Боты не считаются участниками. Убийства ботов и смерти от ботов в статистику не идут.
- Подтверждено живой записью потока (`research/sample-60s.jsonl`): у бота в `KILLER`/`VICTIM` есть `BOT = true`, `BOT_SKILL = 3`, `STEAM_ID = "0"` (строка). У человека `STEAM_ID` — строка вида `"76561198182889645"`. Проверка бота: `BOT == true` в блоках или `STEAM_ID == "0"` в остальных событиях; числовой `0` всё равно принимается благодаря терпимой десериализации.
- Участник матча — человек, у которого в этом матче есть `PLAYER_STATS` без warmup или который фигурирует как `KILLER`/`VICTIM` в событии `PLAYER_DEATH` без warmup **[решение]**. Число людей в матче — количество таких уникальных `STEAM_ID`.

### 3.4 Убийства, смерти, самоубийства, окружение

Убийства и смерти считаются по событиям `PLAYER_DEATH`: одно событие соответствует одной смерти. `PLAYER_KILL` дублирует `PLAYER_DEATH` и не используется. Живая запись подтвердила, что `PLAYER_KILL` и `PLAYER_DEATH` приходят парой с интервалом в несколько миллисекунд. Итоговые `KILLS`/`DEATHS` из `PLAYER_STATS` в расчётах не участвуют, потому что у досрочно вышедших игроков они неполные.

Каждое событие `PLAYER_DEATH` без warmup получает категорию. Правила проверяются по порядку, срабатывает первое подходящее:

| # | Условие | Категория |
|---|---------|-----------|
| 1 | `MOD = SWITCHTEAM` | `ignored`, смертью не считается |
| 2 | `VICTIM` — бот | `ignored` |
| 3 | `KILLER` есть и это бот | `ignored` |
| 4 | `KILLER` есть, `KILLER.STEAM_ID != VICTIM.STEAM_ID`, оба люди | `kill` |
| 5 | `MOD = SUICIDE`, либо `KILLER.STEAM_ID == VICTIM.STEAM_ID` (самоподрыв: `ROCKET_SPLASH`, `GRENADE_SPLASH`, `PLASMA_SPLASH`, `BFG_SPLASH`, `PROXMINE`, `PROXMINE_SPLASH` и т.п.) | `suicide` |
| 6 | `KILLER` нет, `MOD` ∈ {`FALLING`, `LAVA`, `SLIME`, `WATER`, `CRUSH`, `HURT`, `TRIGGER_HURT`, `UNKNOWN`} | `environment` |
| 7 | Всё остальное (например, оружейный `MOD` без `KILLER`) | `ignored`, событие пишется в лог |

Колонки таблицы:

- «Убийства» — число событий `kill`, где игрок указан как `KILLER`.
- «Смерти» — число событий `kill`, где игрок указан как `VICTIM`, то есть смерти от других людей **[решение]**.
- «Самоубийства» — число событий `suicide`, где игрок указан как `VICTIM`.
- «Смерти от окружения» — число событий `environment`, где игрок указан как `VICTIM`.
- «Любимое оружие» — оружие, которым игрок сделал больше всего убийств из колонки «Убийства» (те же события `kill` по засчитанным матчам) **[решение заказчика]**. Оружие берётся из `MOD` (причина смерти), а не из `KILLER.WEAPON`: это оружие в руке в момент смерти, после переключения оно бывает другим. Соответствие `MOD` → оружие (ключи как в `WEAPONS` у `PLAYER_STATS`):
  - `GAUNTLET` → `GAUNTLET`, `MACHINEGUN` → `MACHINEGUN`, `SHOTGUN` → `SHOTGUN`, `LIGHTNING` → `LIGHTNING`, `RAILGUN` → `RAILGUN`, `HMG` → `HMG`, `CHAINGUN` → `CHAINGUN`, `NAILGUN` → `NAILGUN`;
  - `GRENADE`, `GRENADE_SPLASH` → `GRENADE`; `ROCKET`, `ROCKET_SPLASH` → `ROCKET`; `PLASMA`, `PLASMA_SPLASH` → `PLASMA`; `BFG`, `BFG_SPLASH` → `BFG`;
  - `PROXIMITY_MINE`, `PROXMINE`, `PROXMINE_SPLASH` → `PROXMINE` (в модели ql-stats-model написание `PROXMINE`).

  Убийство с другим `MOD` (`TELEFRAG`, `KAMIKAZE`, `UNKNOWN` и т.п.) входит в «Убийства», но оружию не приписывается. Побеждает оружие с наибольшим числом убийств; при равенстве — то, что раньше в списке `GAUNTLET`, `MACHINEGUN`, `SHOTGUN`, `GRENADE`, `ROCKET`, `LIGHTNING`, `RAILGUN`, `PLASMA`, `BFG`, `HMG`, `CHAINGUN`, `NAILGUN`, `PROXMINE`. Если ни одно убийство не приписано оружию, любимого оружия нет (`null`, на странице — «—»).

### 3.5 Лучший стрик

- Стрик — серия убийств (`kill`) без собственной смерти в пределах одного матча. Считается по событиям `PLAYER_DEATH` в порядке `TIME`, а при равном `TIME` — в порядке получения.
- Стрик обнуляет любая собственная смерть игрока, кроме `SWITCHTEAM`: `kill`, `suicide`, `environment` и смерть от бота **[решение]**. Убийство бота стрик не увеличивает.
- Лучший стрик игрока — максимум по всем засчитанным матчам.
- `MAX_STREAK` из `PLAYER_STATS` сохраняется как справочное значение и в расчётах не используется.

### 3.6 Победы

- В `DUEL` победитель — игрок с `WIN = 1` в `PLAYER_STATS`, то есть игрок с бо́льшим `SCORE`. Если `WIN` отсутствует, победителем считается игрок с максимальным `SCORE`.
- В `FFA` победитель — участник с наибольшим `SCORE`. При равенстве очков победа засчитывается всем лидерам. Кандидатами считаются только люди с `PLAYER_STATS`, у которых `QUIT = 0` **[решение, см. открытые вопросы]**.
- «Победы» игрока — сумма таких побед по засчитанным матчам.

### 3.7 Средняя точность

- Точность оружия — `H / S` по блоку `WEAPONS` из `PLAYER_STATS`. Оружие с `S = 0` не участвует в расчёте. Среднее берётся арифметически: все оружия имеют одинаковый вес.
- Способ усреднения по матчам **[решение]**: по каждому оружию суммируются `S` и `H` по всем засчитанным матчам игрока, вычисляется точность оружия, затем берётся среднее по оружиям с `ΣS > 0`.
- Альтернатива — посчитать среднюю точность каждого матча и усреднить её по матчам. Этот вариант не выбран: короткие матчи и редкие выстрелы получают в нём непропорционально большой вес.
- Если у игрока нет ни одного выстрела, точность не показывается (`null`, на странице — «—»).

### 3.8 День и время

- Матч относится к дню по моменту завершения, то есть по времени получения `MATCH_REPORT`, в часовом поясе `Europe/Moscow`.
- «Статистика дня» — текущие календарные сутки по Москве. День сбрасывается в 00:00 по Москве. Выбора другого дня нет.

### 3.9 Идентификация

Игрок определяется по `STEAM_ID`. На странице показывается последний известный ник: ник из самого позднего по времени получения события с этим `STEAM_ID`.

### 3.10 Текущее состояние (live)

Блок «Текущий матч» показывает состояние сервера прямо сейчас, независимо от того, будет ли матч засчитан в статистику. Это live-картинка, а не статистика. Поэтому правила 3.1–3.3 к блоку не применяются: показываются любые режимы, включая командные, а также warmup и боты.

**Состояния:**

| Состояние | Условие |
|-----------|---------|
| «Нет связи с сервером» | ZMQ-соединение разорвано дольше `QLSTATS_LIVE_OFFLINE_SECS` (по умолчанию 15 с) по данным монитора сокета или после неуспешного переподключения. Имеет приоритет над остальными состояниями. Это не то же самое, что пустой сервер. |
| «Сервер пуст» | Связь есть, в списке участников нет ни одного человека. На пустом сервере событий нет, поэтому состояние определяется по списку участников, а не по тишине. Бот без людей событий не генерирует, поэтому одинокий бот не делает сервер «непустым». |
| «Разминка» | Есть хотя бы один человек, матч не начат: последние события пришли с `WARMUP = true` или после `MATCH_REPORT` ещё не было `MATCH_STARTED`. |
| «Идёт матч» | Получен `MATCH_STARTED`, а `MATCH_REPORT` с тем же GUID ещё не пришёл. |

**Поля блока:**
- карта (`MAP`);
- режим (`GAME_TYPE`, `FACTORY_TITLE`);
- время с начала матча — от момента получения `MATCH_STARTED`;
- лимиты, если применимы: `FRAG_LIMIT` и `TIME_LIMIT`, а для командных режимов ещё `CAPTURE_LIMIT` (CTF, ONEFLAG), `ROUND_LIMIT` (CA, FT, AD) или `SCORE_LIMIT` (DOM). Нулевой лимит не показывается;
- список участников: ник, признак бота, команда (только в командных режимах), текущий счёт.

В разминке события не содержат `MAP` и `GAME_TYPE`. Поэтому до `MATCH_STARTED` карта и режим не показываются **[решение]**.

**Участники:**
- Список строится из `MATCH_STARTED.PLAYERS`, затем меняется по `PLAYER_CONNECT`, `PLAYER_DISCONNECT` и `PLAYER_SWITCHTEAM`. Игроки, впервые замеченные в `PLAYER_DEATH`, `PLAYER_MEDAL` или `PLAYER_STATS` текущего GUID, тоже добавляются.
- Бот — `STEAM_ID = "0"` (или `BOT = true` в блоках KILLER/VICTIM). Бот помечается меткой.
- Команда хранится нормализованной: `free`, `red`, `blue`, `spectator`. Живая запись показывает два формата: число в `MATCH_STARTED.PLAYERS.TEAM` (0 — free) и строку в `PLAYER_SWITCHTEAM` (`"FREE"`, `"SPECTATOR"`).
- Зрители (`spectator`) в список не входят и показываются отдельной строкой «зрители: N» **[решение]**.
- Живая запись показала, что `PLAYER_CONNECT`/`PLAYER_DISCONNECT` у бота не приходят. Поэтому бот попадает в список из `MATCH_STARTED.PLAYERS` или из событий смерти и медалей, а удаляется при сбросе состояния (`MATCH_REPORT`, уход последнего человека) или при следующем `MATCH_STARTED` (ограничение, раздел 6).

**Текущий счёт.** `SCORE` приходит только в `PLAYER_STATS` в конце матча, поэтому live-счёт вычисляется из `PLAYER_DEATH` текущего матча (`WARMUP = false`):
- **FFA, DUEL и другие некомандные режимы:** +1 за убийство другого игрока (человека или бота), −1 за самоубийство (категория `suicide` из 3.4), −1 за смерть от окружения (категория `environment`, в QL она тоже даёт −1). `SWITCHTEAM` не учитывается. Здесь, в отличие от статистики, боты и убийства ботов учитываются, потому что это реальный игровой счёт.
- **Командные режимы:** показывается число убийств игроком соперников, `TEAMKILL = true` не считается. Командный счёт не показывается, потому что данных о нём до `MATCH_REPORT` нет **[ограничение]**.
- Live-счёт приближённый и может расходиться с итоговым `SCORE` на 1–2 (особенности начисления, потерянные события). Итоговый счёт берётся только из `PLAYER_STATS`. В интерфейсе счёт помечается как текущий, а не итоговый.
- В разминке счёт не ведётся (`null`). При переходе в «Идёт матч» он обнуляется.

**Сброс и устаревание:**
- По `MATCH_REPORT` текущий матч закрывается. Состояние становится «Разминка», если остались люди, или «Сервер пуст».
- Если состояние «Идёт матч» длится дольше `TIME_LIMIT + 5 мин` (при `TIME_LIMIT > 0`), считается, что `MATCH_REPORT` потерян при обрыве, и матч закрывается **[решение]**.

**Хранение и восстановление:**
- Live-состояние хранится только в памяти и в БД не пишется. `recompute` его не затрагивает.
- При старте приложения состояние восстанавливается из `raw_events` **[решение]**: события после последнего `MATCH_REPORT` (по `id`) прогоняются через тот же автомат состояний, затем применяется правило устаревания. Это дёшево: обычно десятки–сотни строк.

## 4. Интерфейс

Веб-интерфейс на русском языке, публичный, без авторизации. На первом этапе работает по HTTP, без домена и https.

- **«Текущий матч»** — первый блок страницы, над «Статистикой дня». Состояния, поля и правила описаны в 3.10. Блок обновляется раз в 30 с, отдельно от остальных блоков, и показывает индикатор «live».
- **«Статистика дня»**:
  - число засчитанных матчей за текущие сутки;
  - участник(и) с наибольшим числом побед за день;
  - участник(и) с наибольшим числом убийств за день.

  При равенстве показываются все лидеры. Если за день не было матчей, выводится «нет матчей».
- **«Статистика за всё время»** — те же три показателя за весь период.
- **Таблица участников** с колонками: ник, матчи, убийства, смерти, лучший стрик, победы, средняя точность, самоубийства, смерти от окружения, любимое оружие (10 колонок). В таблице только игроки хотя бы с одним засчитанным матчем.
  - Сортировка по любому столбцу на клиенте **[решение]**. Число участников на одном сервере небольшое (сотни строк), поэтому таблица целиком приходит одним ответом.
- **Обновление** **[решение, изменено 2026-10-19]**: «Текущий матч» опрашивает `/api/live` каждые 30 с, статистика опрашивает API тоже каждые 30 с; оба — дополнительно при возвращении на вкладку. Первоначально `/api/live` опрашивался раз в 5 с; 2026-10-18 автообновление было полностью убрано из-за фоновой нагрузки и расхода лимитов туннеля, 2026-10-19 возвращено с единым интервалом 30 с. Используется `ETag`/`If-None-Match`: если данные не изменились, сервер отвечает `304`. От SSE отказались: данные меняются раз в несколько минут (при завершении матча), а 300 постоянных соединений сложнее в эксплуатации, чем дешёвый опрос с `304`.

## 5. Нефункциональные требования

- **Язык.** Rust, стабильный toolchain (установлен 1.99). Сторонние крейты разрешены.
- **Устойчивость к обрыву ZMQ.**
  - Приложение переподключается автоматически: `ZMQ_RECONNECT_IVL` плюс пересоздание сокета, если долго нет данных или сокет вернул ошибку.
  - Подключения, обрывы и переподключения пишутся в лог.
  - PUB не буферизует сообщения, поэтому события на время обрыва теряются. Матч без `MATCH_STARTED` не засчитывается. Матч с `MATCH_STARTED` и `MATCH_REPORT`, но с пропусками в середине, засчитывается по имеющимся данным (см. открытые вопросы).
  - Обрыв ZMQ не останавливает веб-сервер.
- **Терпимая десериализация.**
  - Булевы значения принимаются как `true/false` и как `0/1`.
  - `STEAM_ID` принимается и строкой, и числом, внутри хранится строкой.
  - Неизвестные поля и типы событий не ломают разбор.
  - Отсутствующие необязательные поля дают `None`.
  - Невалидный UTF-8 декодируется lossy.
  - Сырой JSON сохраняется до разбора.
- **Пересчёт.** Отдельная CLI-команда (`qlstats recompute`) пересоздаёт все нормализованные данные и агрегаты из `raw_events`. Результат должен совпадать с инкрементальным учётом. Live-состояние пересчёт не затрагивает.
- **Производительность.**
  - Веб выдерживает стресс-тест: 300 одновременных зрителей страницы.
  - `/api/live` отдаётся из памяти, без обращения к БД.
  - Расчётная нагрузка от 300 зрителей: `/api/live` раз в 30 с с каждого — 10 RPS, `/api/summary` и `/api/players` раз в 30 с — ещё 20 RPS. Итого около 30 RPS в установившемся режиме, большая часть ответов — `304`. Первоначальный расчёт для `/api/live` раз в 5 с (около 80 RPS) остаётся верхней оценкой; стресс-тест 2026-10-18 выполнен по ней (`docs/perf/`).
  - Измеряются нагрузка в простое и под нагрузкой. Методика:
    - **Инструменты:** `oha` для насыщения отдельных эндпоинтов, `k6` для сценария «зритель» (загрузка страницы, затем опрос `/api/live` каждые 5 с и `/api/summary` + `/api/players` каждые 30 с). Генератор нагрузки запускается на другой машине или хотя бы ограничивается по ядрам, чтобы не делить CPU с сервисом.
    - **Сценарии:**
      - простой — 10 мин без HTTP-трафика, ZMQ подключён;
      - реалистичный — 300 VU k6 в течение 10 мин. Параллельно идёт `qlstats replay` записанного матча, чтобы live-состояние менялось и часть ответов `/api/live` была `200`, а не `304`;
      - насыщение — `oha -c 300 -z 60s` по `/api/live`, `/api/summary`, `/api/players`, `/`, с `If-None-Match` и без него.
    - **Метрики:**
      - latency p50/p95/p99;
      - RPS;
      - доля ошибок (не-2xx/304, таймауты);
      - CPU процесса (%) и RSS (МБ), снимаются раз в 1 с (`pidstat -r -u -p <pid> 1` или `ps -o %cpu,rss`), а также пиковые значения;
      - число открытых fd.
    - **Целевые значения** **[решение]**:
      - в реалистичном сценарии (около 80 RPS, из них 60 на `/api/live`) ошибок 0, p99 < 100 мс для всех эндпоинтов, CPU < 10 % одного ядра;
      - в насыщении ошибок 0, p95 < 50 мс, для `/api/live` — не меньше 5000 RPS (запас в 80 раз от расчётных 60 RPS);
      - RSS < 100 МБ;
      - в простое CPU < 1 %.
    - Результаты фиксируются вместе с характеристиками железа и версией сборки (`--release`).
- **Деплой.** Один бинарник и файл SQLite. Конфигурация берётся из env или `.env`. Рекомендуется systemd-unit с `Restart=always`.
- **Логирование.** Структурированные логи в stdout (journald). Уровень задаётся через `RUST_LOG`.

## 6. Открытые вопросы

1. **RACE.** Учитывать ли его как некомандный режим? Побед там нет, если нет очков, а лучшее время — другая метрика. Пока `RACE` не засчитывается.
2. **Потерянный `MATCH_STARTED`.** Матч, начало которого пропало из-за обрыва, сейчас теряется. Можно было бы засчитывать его по `MATCH_REPORT` и `PLAYER_STATS`, если в сыром потоке есть события `PLAYER_DEATH` с тем же GUID. Нужно решение заказчика.
3. **Матч с пропуском в середине** (обрыв во время игры). Убийства и стрики в нём неполные. Засчитывать как есть или помечать такой матч?
4. **TELEFRAG** в модели не найден. Если он придёт с `KILLER` — это `kill`, без `KILLER` — `ignored` (с записью в лог). `KAMIKAZE` и прочие `MOD` вне списков классифицируются по наличию `KILLER`.
5. **Победа при выходе.**
   - FFA: учитывать ли вышедших (`QUIT = 1`) среди кандидатов на победу? Сейчас не учитываются.
   - DUEL: при форфейте (`"Players have forfeited."`, `ABORTED = false`) победа присуждается по `WIN`.
6. **Форфейт** с `ABORTED = false` засчитывается по правилу 3.1. Нужно ли дополнительно отсекать короткие матчи (например, по `GAME_LENGTH`)?
7. **`GAUNTLET` и `OTHER_WEAPON` в средней точности.** Сейчас учитываются при `S > 0`. Проверить, что `S` у гантлета осмысленно.
8. **Написания `ONEFLAG`/`HAR`** и реальные ключи событий — сверить с живым потоком.
9. **Спектаторы в `MATCH_STARTED.PLAYERS`.** Сейчас они не считаются участниками: участие определяется по `PLAYER_STATS` и `PLAYER_DEATH`.
10. **Бот в live-блоке.** Бот не шлёт `PLAYER_CONNECT`/`PLAYER_DISCONNECT`. Если в разминке бот ушёл из-за прихода второго человека, он может оставаться в списке до `MATCH_STARTED`. Варианты: удалять бота при появлении второго человека (опираясь на настройку сервера) или оставить как есть.
11. **Расхождение live-счёта с итоговым.** Точный набор правил начисления QL (например, за `KAMIKAZE`, `TELEFRAG`, смерть от бота-«окружения») сверить на живой записи, сравнив вычисленный счёт с `SCORE` из `PLAYER_STATS`.

### 6.1 Принятые решения по открытым вопросам (2026-10-18)

- 1 (RACE): не засчитывается до появления запроса.
- 2 и 3 (обрывы): матч без `MATCH_STARTED` не засчитывается; матч с пропуском в середине засчитывается как есть, но помечается `incomplete = 1`, если между соседними событиями GUID был разрыв соединения.
- 5 (победа при выходе): FFA — вышедшие не кандидаты; DUEL — по `WIN`.
- 6 (форфейт): засчитывается, отсечения по длине нет.
- 7 (GAUNTLET): живой поток показал `S = 0` у гантлета, он исключается автоматически правилом `S > 0`.
- 9 (спектаторы): не участники.
- Любимое оружие (добавлено по запросу заказчика): по засчитанным убийствам из `MOD`, тай-брейк по фиксированному порядку оружия (3.4). Для матчей, записанных до обновления, значение появляется после `qlstats recompute`.
- 4 и 8: проверяются по записи живого потока (`docs/research/sample-long.jsonl`) при имплементации.
